# 动态证据模块 — 设计说明

日期：2026-08-29  
状态：待实现（分三档：M5a 对话能分析 → M5b 证据选得对 → M5c 结构出得对，见同目录 milestones）  
取代：同目录 [`2026-08-29-汇报不返工-design.md`](./2026-08-29-汇报不返工-design.md) 中「固定 8 页 / 漏斗或进度作为默认核心」的产品定义。技术底座仍沿用原文：单体 Next.js、模型只组织故事、数字由代码计算、PptxGenJS 原生图表、不编造。

## 1. 问题与目标

上一版把「业务漏斗 + 项目进度」当成领导永远要看的东西。真实需求不是填一张漏斗表，而是根据自己做过的内容，把领导这次必须判断的问题讲清楚。

产品核心：

> 先识别领导在本次汇报中需要判断的问题，再选择最适合支撑这个判断的证据结构。

业务漏斗只是「用户使用、产品转化、流程流失」类汇报的一种证据组件。不能作为所有场景的固定核心，也不能要求每次汇报都填写或展示漏斗。

成功标准分三档，见同目录 milestones 的 M5a / M5b / M5c。

- **M5a（对话能分析）：** 贴一段对话就能指出领导要判断的问题、风险点和下一步，用户能改主线再分析。创建页没有漏斗或必填进度。这一档能跑即可演示。
- **M5b（连接 Notion）：** 从 Notion 选页面或贴链接，把正文导入「工作对话或材料」，再走现有分析。只读不写回。
- **M5c（证据和结构）：** 完整验收。建议 1–3 个证据模块；不同汇报目的生成不同页结构；主汇报 4–7 页；Demo 至少各有一个漏斗场景和一个非漏斗场景；不为填满结构而编造数据或展示空图表。

## 2. 范围

做：

- 创建时提交我最初的汇报背景 + 本次工作材料（可粘贴纪要、说明、对话、数据摘录；M5b 起可从 Notion 选页面导入）
- 系统产出 `ReportAnalysis`：管理问题、汇报意图、结论、建议证据、发现、行动、拍板事项
- 第二步「确认汇报主线」：用户确认、编辑、删除或替换证据
- 按 `ReportIntent` 动态生成网页幻灯片，需要时再导出可编辑 PPTX
- 两套可重复 Demo

不做：

- 把漏斗或进度做成创建页必填表单
- 固定五页或八页模板套所有场景
- 为了出图而发明漏斗阶段或空 KPI 页
- 自定义母版、在线画布、多 Agent、账号体系

## 3. 架构原则

```
材料 → ReportAnalysis → 用户确认 → DeckSpec → 网页预览 / PPTX
```

禁止：材料 → LLM → PPTX。

分工：

- LLM：识别管理问题、汇报意图、一句话结论、关键发现、下一步、拍板事项；建议 1–3 个证据类型并抽出候选数据
- TypeScript：漏斗四条件门禁、漏斗转化率计算、空证据过滤、Deck 结构模板、Fact 绑定、数字不编造
- 用户：在确认页改正文和证据，再生成幻灯片

数字仍走 Fact。漏斗计算逻辑保留，但只有 `EvidenceType === "funnel"` 时才调用。

## 4. 证据模块

第二步不固定显示业务漏斗，改为「系统建议使用的证据」。系统根据汇报目的、上传材料和数据，自动选择一到三种最合适的证据模块。没有抽到数据的模块不进数组，也不渲染空组件。

```ts
type EvidenceType =
  | "funnel"
  | "before_after"
  | "trend"
  | "milestone"
  | "goal_vs_result"
  | "impact_metrics"
  | "risk"
  | "options_comparison"
  | "qualitative_insight";
```

每种类型有独立 payload、独立确认卡片、独立网页预览组件、独立 PPTX 渲染器。不要在一个组件里用大量条件判断切换九种形态。

### 4.1 funnel

适用：产品转化、用户使用链路、流程完成率、定位最大流失环节。

示例：

```text
模板入口点击 → 使用模板 → 成功生成 Design
```

payload：有序阶段名 + 数量；代码计算相邻转化率和总转化率。

### 4.2 before_after

适用：效率提升、技术改造、流程优化、成本变化。

示例：

```text
交付周期：3个月 → 2周
测试耗时：60分钟 → 20分钟
```

payload：指标名、之前、之后；单位可写在值里或单独字段。

### 4.3 trend

适用：用户量、故障率、收入或使用量、连续周期指标。

payload：同一口径的周期点。口径不可比则不推荐本模块。

### 4.4 milestone

适用：项目进展同步、跨团队项目、上线计划、多阶段交付。

只展示会影响交付判断的关键节点，不展示普通任务清单。

### 4.5 goal_vs_result

适用项目复盘：原定目标、实际结果、达成或未达成、差异原因。

### 4.6 impact_metrics

适用展示项目价值：覆盖国家数量、用户规模、节省时间、减少成本、提升稳定性、增加收入。

### 4.7 risk

适用：项目风险同步、上线风险、资源不足、依赖阻塞。

必须包含风险、影响、概率、缓解方案。

### 4.8 options_comparison

适用请求领导拍板：可选方案、收益、成本、风险、推荐方案。

### 4.9 qualitative_insight

适用没有完整量化数据，但有明确用户反馈、客户访谈或业务观察的情况。

必须明确标记这是定性证据，不能包装成量化结论。

## 5. 业务漏斗的启用条件

只有同时满足以下条件，才建议展示业务漏斗：

1. 汇报问题与用户使用、转化或者流程流失有关
2. 材料中存在两个以上有顺序关系的业务步骤
3. 各步骤数据属于相同或者可比较的数据口径
4. 漏斗能够直接帮助领导判断项目效果或下一步行动

任一条件不满足：

- 不显示空漏斗
- 不要求用户填写漏斗
- 不得为了生成图表而强行创造漏斗

系统可以提示：

> 本次汇报不适合使用业务漏斗，建议使用「前后对比 + 核心影响指标」。

四条件由 TypeScript 再滤一遍。LLM 即使返回了 `funnel`，门禁失败也要从 `recommendedEvidence` 中移除，并写入上述提示。

## 6. 数据模型

```ts
type ReportIntent =
  | "result"
  | "progress"
  | "retrospective"
  | "decision"
  | "product_conversion";

type EvidenceConfidence = "high" | "medium" | "low";

interface EvidenceBlock {
  id: string;
  type: EvidenceType;
  title: string;
  reason: string;
  sourceRefs: string[];
  confidence: EvidenceConfidence;
  data: EvidencePayload;
}

interface ReportAnalysis {
  leaderQuestion: string;
  intent: ReportIntent;
  coreConclusion: string;
  recommendedEvidence: EvidenceBlock[];
  keyFindings: string[];
  risks: string[];
  nextActions: string[];
  decisionAsk?: string;
  missingInformation: string[];
  excludedDetails: string[];
  evidenceHint?: string;
}
```

`recommendedEvidence` 最多 3 条。`data` 按 `type` 收窄，不用松散的 `unknown` 在运行时猜形状。

分类型 payload：

```ts
type FunnelPayload = {
  stages: { name: string; value: number; unit?: string }[];
};

type BeforeAfterPayload = {
  pairs: { metric: string; before: string; after: string }[];
};

type TrendPayload = {
  seriesLabel: string;
  points: { period: string; value: number; unit?: string }[];
};

type MilestonePayload = {
  items: { name: string; date?: string; status: string; deliveryImpact: string }[];
};

type GoalVsResultPayload = {
  rows: { goal: string; result: string; met: boolean; gapReason?: string }[];
};

type ImpactMetricsPayload = {
  metrics: { label: string; value: string; meaning?: string }[];
};

type RiskPayload = {
  items: {
    risk: string;
    impact: string;
    probability: string;
    mitigation: string;
  }[];
};

type OptionsComparisonPayload = {
  options: { name: string; benefit: string; cost: string; risk: string }[];
  recommendation: string;
};

type QualitativeInsightPayload = {
  insights: string[];
  caveat: "定性证据，不能当作量化结论";
};

type EvidencePayload =
  | FunnelPayload
  | BeforeAfterPayload
  | TrendPayload
  | MilestonePayload
  | GoalVsResultPayload
  | ImpactMetricsPayload
  | RiskPayload
  | OptionsComparisonPayload
  | QualitativeInsightPayload;
```

项目存储增加 `analysis` JSON。旧 Brief 中的固定 `funnel` / 必填 `progress` 不再是产品主模型；漏斗阶段数字只作为 `FunnelPayload` 的来源。

## 7. 用户流程

```text
创建（汇报背景 + 材料）
  → 分析（问题 + 意图 + 证据）
  → 确认汇报主线
  → 按意图生成结构
  → 预览
  → 可选导出 PPT
```

向导四步：创建 → 确认主线 → 预览 → 导出。确认页复用 `/projects/:id/outline`。

### 7.1 创建

必填：我最初的汇报背景（这次想讲什么、给谁讲、卡在哪）。  
选填：本次工作对话/材料文本；时长；txt/md/csv 文件。M5b 起也可从 Notion 选页面或贴链接导入正文。

不出现：业务漏斗表单、必填进度清单、把漏斗当作关注点芯片。

创建页提供两个 Demo 按钮，分别灌入漏斗场景和非漏斗场景，不共用同一份材料。

### 7.2 确认汇报主线

页面包含：

1. 核心管理问题
2. 系统判断的汇报目的
3. 一句话结论
4. 系统建议使用的证据
5. 关键发现
6. 下一步行动
7. 需要领导拍板的事项

「系统建议使用的证据」区域：

- 显示推荐的证据类型
- 解释为什么推荐
- 展示提取出的数据
- 允许用户确认、编辑、删除
- 允许用户替换为其他证据类型
- 不显示没有数据的空组件

示例：

```text
推荐证据：前后对比

推荐原因：
本次汇报重点是证明项目复用带来的交付效率提升，
材料中存在菲律宾和印度尼西亚两个阶段的交付周期。

提取结果：
首次交付：约3个月
复用后交付：约2周
```

用户确认后，才用这份 `ReportAnalysis` 生成 Deck。预览页仍可写一句意见重生成，但不得借机补上材料里没有的漏斗。

## 8. 动态汇报结构

不要固定所有汇报都生成相同的五页或八页。根据 `intent` 选结构。封面另计；正文建议 4 至 7 页，不要为凑页数注水。缺材料就少页。

### 结果汇报 `result`

1. 核心结论
2. 关键指标或业务结果
3. 原因分析
4. 下一步行动
5. 需要的支持

### 进度汇报 `progress`

1. 当前整体状态
2. 已完成的关键里程碑
3. 主要阻塞和风险
4. 预计交付时间
5. 需要领导协调的事项

### 项目复盘 `retrospective`

1. 原定目标与最终结果
2. 做对了什么
3. 哪些目标没有达成
4. 原因和经验
5. 下一阶段调整

### 决策汇报 `decision`

1. 需要决定的问题
2. 背景和限制条件
3. 方案对比
4. 推荐方案及依据
5. 不同决策的影响

### 产品使用或转化汇报 `product_conversion`

1. 核心结论
2. 用户使用漏斗
3. 最大流失环节
4. 原因假设
5. 优化行动

`product_conversion` 是唯一默认包含漏斗页的结构，且仍须通过第四节的四条件。其他意图即使模型想加漏斗页，门禁失败也不能生成。

证据模块映射到对应 slide type。有证据才有该页；没有对应证据就跳过该节，不要留「资料未提供」空图来占位——缺的信息写进 `missingInformation`，必要时用一句话说明，不用空图表填版面。

## 9. 生成与校验

Deck 生成只消费用户确认后的 `ReportAnalysis`。

硬性规则：

- 正文数字必须能追溯到 Fact 或用户确认过的证据值
- 禁止裸数字幻觉
- 禁止为凑 `exactSlides` / 最小页数而 pad 空 funnel、空 KPI、空 trend
- `type === "funnel"` 的页必须带有至少两个有效阶段；否则整页删除
- `qualitative_insight` 的页面和卡片必须出现定性标记

漏斗转化率仍由现有计算逻辑产出 Fact，仅在存在漏斗证据时调用。

## 10. Demo

### Demo A · 漏斗场景

主题：模板使用与 Design 生成转化。

```text
模板入口点击 → 使用模板 → 成功生成 Design
```

- `intent`：`product_conversion`
- 证据必须包含 `funnel`
- 用于验收漏斗类结构、流失环节和优化行动

### Demo B · 非漏斗场景

主题：跨国家项目复用与交付效率汇报。

- `intent`：`result`
- `recommendedEvidence` 固定三条：`impact_metrics`、`before_after`、`milestone`
- 风险写入 `risks`，下一阶段计划写入 `nextActions`，不要为了塞进第四个证据位而改用漏斗
- `before_after` 至少包含：首次交付约 3 个月 → 复用后约 2 周
- `milestone` 为国家上线关键节点，不是日常任务
- 确认页和 Deck **不得出现**业务漏斗或空漏斗表单

创建页两个按钮分走这两套材料。

## 11. 验收

完整清单对应 **M5c**。M5a 只验收「对话能分析、能改主线」；M5b 只验收证据推荐与漏斗门禁。

- 漏斗不是必填项
- 非转化类项目不会显示漏斗
- 系统能够推荐其他证据形式，并给出推荐原因和提取结果
- 不同汇报目的会生成不同结构
- Demo 至少包含一个漏斗场景和一个非漏斗场景
- 页面不会为了填满结构而编造数据或展示空图表
- 用户可在确认页把某条证据换成其他类型；换成 `funnel` 时仍过四条件，否则提示不适合使用漏斗
- Demo B 走完后，分析 JSON、确认页、预览、导出 PPT 均无 `funnel`

## 12. 实现顺序

按 M5a → M5b → M5c 推进。产品定义不变，只改先做什么。

### M5a · 对话能分析

1. 创建页改为「我最初的汇报背景」+ 一段工作对话/材料；去掉必填进度和漏斗表单
2. `ReportAnalysis` 先落地主线字段：`leaderQuestion`、`intent`、`coreConclusion`、`keyFindings`、`risks`、`nextActions`、`decisionAsk`、`missingInformation`
3. Flash 分析对话；确认页展示上述 7 项，可编辑后重新分析
4. 用现有文字页（结论 / 问题 / 行动）出极简预览，证明链路通

### M5b · 连接 Notion

5. 服务端用 Notion Internal Integration（`NOTION_API_KEY`）搜索/读取已分享页面
6. 创建页支持选页面或粘贴链接，把块内容转成纯文本写入材料
7. 导入后仍可编辑，再走 M5a 分析；不写回 Notion，不做 OAuth

### M5c · 证据和结构

8. 补齐九种 `EvidenceType` payload 与漏斗四条件门禁；确认页可编辑/替换证据
9. 按 `ReportIntent` 选结构模板生成 Deck；正文 4–7 页，禁止 pad 空页
10. 九种证据的独立预览组件与 PPTX 渲染器；两套 fixtures/demo，按第 11 节走两遍

## 13. 明确不采用的做法

- 只靠 Prompt 约束「不要乱加漏斗」：模型仍会为了完整感硬造漏斗
- 继续把 `Brief.funnel` / 必填进度当作主输入：用户还是在填结构，不是在讲事情
- 所有意图共用同一套「结论 / 漏斗 / 进度 / 建议 / 行动」五页
