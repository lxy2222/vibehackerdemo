# 汇报不返工 — 设计说明

日期：2026-08-29  
状态：已被取代，仅备查。当前产品定义见 [`2026-08-29-动态证据模块-design.md`](./2026-08-29-动态证据模块-design.md)；里程碑见 [`2026-08-29-汇报不返工-milestones.md`](./2026-08-29-汇报不返工-milestones.md)。  
本文是第一版「固定 8 页 / 表格算数 / 三问澄清」方案。其中 M1 / M2 已被确认主线取代；**M4 套设计风格、M5c 证据和结构已取消，不再实现。**

## 1. 问题与目标

职场人做项目汇报、活动复盘、阶段总结时，真正耗时的不是排版，而是需求没说清、材料太零散、做完被领导打回。第一版产品把「澄清 → 整理事实 → 生成可编辑 PPT → 对照验收」做成一条闭环。

成功标准（MVP 可演示即停）：

- 从输入到 PPTX 大约 60 秒
- 最多 3 个澄清问题
- 固定 8 页，文本和图表可在 PowerPoint / WPS 中编辑
- 所有数字能追溯到上传文件；没有数据时显示「资料未提供」，不编造
- 每页有演讲备注；验收能标出至少一个阻塞问题（在故意缺料的案例上）
- 有一套可重复演示的固定案例

## 2. MVP 范围

只做一种场景：项目 / 活动 / 阶段工作复盘。

输入：

- 领导原话（必填）
- 会议纪要 `.txt` / `.md`（可选）
- 业务数据 `.csv` / `.xlsx`（可选）
- 汇报时长，默认 10 分钟

输出：

- 最多 3 个澄清问题
- 8 页可编辑 `.pptx`
- 图表、结论、行动建议、演讲备注、数据来源
- 验收报告 + 可复制给领导的交付消息

明确不做：PDF/DOCX/旧 PPT 解析、自定义模板、在线画布编辑、飞书/企微/邮箱、账号体系、多 Agent、装饰配图、Slidev。

表格和纪要都可以缺。没有表格时，KPI / 趋势 / 对比三页保留版式并显示「资料未提供」；结论、诊断、建议、行动计划走定性。验收把「缺少量化」标成普通建议；只有领导点名要看的指标材料里没有，才算阻塞。

## 3. 架构原则

单体 Next.js 应用。模型只负责理解、提炼、组织故事；代码负责数据计算、Schema 校验和 PPT 排版。

```
RequirementSpec → Facts[] → DeckSpec → PPTX
```

禁止：用户文件 → LLM → PPTX。

六层：页面 → 项目/文件 API → 解析与 Fact Engine → LLM 结构化工作流 → DeckSpec 校验 → PptxGenJS 渲染。

技术选型：

| 模块 | 方案 |
| --- | --- |
| 前端与 API | Next.js App Router + TypeScript + Tailwind + shadcn/ui |
| 校验 | Zod |
| LLM | OpenAI 兼容 SDK，默认 DeepSeek V4 |
| 表格 | SheetJS |
| PPTX | PptxGenJS（原生文本、图表、备注，不是截图） |
| 数据 | SQLite + Drizzle |
| 文件 | 本地 `uploads/`、`artifacts/` |
| 测试 | Vitest + Playwright |

## 4. 大模型

默认提供商：DeepSeek，`base_url = https://api.deepseek.com`，Key 仅服务端 `DEEPSEEK_API_KEY`。

| 调用 | 用途 | 模型 |
| --- | --- | --- |
| 1 | 需求识别 + 澄清问题 | `deepseek-v4-flash` |
| 2 | 生成 DeckSpec | `deepseek-v4-pro` |
| 3 | 语义验收 + 交付消息 | `deepseek-v4-pro` |

三次调用都关闭 thinking。不用 `deepseek-chat` / `deepseek-reasoner` 旧 ID。

Chat Completions 使用 `response_format: { type: "json_object" }`（不保证字段级 schema）。Prompt 必须包含单词 `json` 和示例结构。返回后用 Zod 校验；失败或空内容自动重试 1 次。`temperature = 0`（第三次交付文案允许 0.3）。

数字防幻觉不依赖模型：结论禁止裸数字，渲染时从 Fact 填入。

## 5. 核心数据结构

### RequirementSpec

模型提取不到的字段必须是 `null`，禁止猜测。

```ts
type RequirementSpec = {
  goal: string | null;
  audience: string | null;
  deadline: string | null;
  durationMinutes: number;
  reportType: "project_review";
  focusMetrics: string[];
  expectedDecisions: string[];
  requiredSections: string[];
  constraints: string[];
  missingFields: string[];
  clarificationQuestions: string[]; // 最多 3 条
};
```

### Fact

所有数字由 TypeScript 计算。无表格时 `facts = []`。

```ts
type Fact = {
  id: string;
  sourceId: string;
  label: string;
  value: number | string;
  unit: string | null;
  period: string | null;
  dimensions: Record<string, string>;
  locator: { sheet?: string; range?: string; paragraph?: number };
  calculation?: string;
};
```

第一版固定计算：总和/均值、当前与上一周期、环比、Top/Bottom 3、渠道占比、目标完成率（有目标列时）、成本/收入/转化率、异常升降。

### DeckSpec

不含 x/y/fontSize。图表不含数据点。

```ts
type ChartSpec = {
  type: "bar" | "line" | "bar_horizontal";
  factRefs: string[];
};

type SlideSpec = {
  id: string;
  type:
    | "cover"
    | "executive_summary"
    | "kpi_overview"
    | "trend"
    | "comparison"
    | "diagnosis"
    | "recommendations"
    | "action_plan";
  headline: string;
  takeaway: string;
  bullets: string[];
  factRefs: string[];
  chart?: ChartSpec;
  speakerNotes: string;
  estimatedSeconds: number;
};

type DeckSpec = {
  title: string;
  subtitle: string;
  slides: SlideSpec[];
};
```

模型只能选择 `type` 和填写文案/引用。`takeaway` 示例：`"转化率显著增长"` + `factRefs: ["fact_conversion_growth"]`。禁止写成 `"转化率增长了 35%"`。校验器拒绝正文中无法对应 Fact 的数字。

8 页固定顺序：封面、核心结论、指标总览、趋势、对比、问题与原因、建议、行动计划。无对应 Fact 时，kpi/trend/comparison 走「资料未提供」布局，页数仍为 8。

## 6. 用户流程

1. **创建**：粘贴领导原话；时长默认 10 分钟；可选上传纪要和表格；点「分析需求」。
2. **确认需求**：展示识别结果；回答最多 3 个澄清问题；有表格且列识别置信度低时确认时间列/维度列/指标列。
3. **大纲**：8 页标题、结论、引用事实；可改标题和结论，不能手填裸数字；点「生成 PPT」。
4. **验收**：可提交 / 需要修改；下载 PPTX；复制交付消息。

澄清问题只问会改变结论、结构或数据口径的缺口。不问视觉偏好。

纪要解析：按标题和段落切块，不做第四次 LLM 摘要。表格：SheetJS → 表头/类型检测 → 必要时用户确认 → Fact Engine。发给模型的是列定义、概况、已算好的 Facts、少量样本行，不是整表。

`/generate` 同步执行。只有明显超过一分钟时再加队列。

项目状态：`draft → analyzing → needs_clarification → ready → generating → review_required | completed → failed`。

API：

```
POST   /api/projects
POST   /api/projects/:id/files
POST   /api/projects/:id/analyze
PATCH  /api/projects/:id/requirements
POST   /api/projects/:id/generate
GET    /api/projects/:id
GET    /api/decks/:id/download
POST   /api/decks/:id/audit
```

## 7. PPTX 渲染

每种 `slide.type` 一个渲染器（最多两个布局变体：有数据 / 资料未提供）。Slide Master 固定 16:9。

色卡：背景 `#fdfdfe`，标题 `#452255`，主色 `#0b8571`，强调 `#ef8d37`，辅助 `#cfad20`，浅色 `#8ecccd`。

中文字体优先 `Microsoft YaHei`，并在第一步用写死的 DeckSpec 验证 PowerPoint / Keynote / WPS。每页一个核心结论，标题不超过 24 字，最多 5 条 bullet，底部显示来源，备注约 40–80 秒讲稿。图表仅柱状、折线、条形，且为 PowerPoint 原生 chart。

不使用 Slidev：其 PPTX 导出是整页图片，无法满足「可编辑文字和图表」。

## 8. 验收

代码验收必须通过：正好 8 页；所有 `factRefs` 存在；图表数值与 Fact 一致；结论中的数字可追溯；字数限制；讲解时长总和对照用户要求（超出则阻塞或降为建议，以是否严重影响交付为准：超过时长 20% 为阻塞）；PPTX 非空；领导点名指标无 Fact 则为阻塞。

LLM 验收：是否回答原始问题；结论是否由事实支持；建议与问题是否对应；纪要中的重要风险是否遗漏；可能被追问的点；交付消息。

```ts
type AuditReport = {
  status: "ready" | "needs_revision";
  blockers: string[];
  suggestions: string[];
  likelyFollowups: string[];
  deliveryMessage: string;
};
```

无表格时「缺少量化依据」进入 `suggestions`，不进入 `blockers`，除非 `focusMetrics` 中有材料无法支撑的指标。

## 9. 安全

- API Key 只在服务端
- 扩展名 + MIME 校验；单文件 10MB；最多 3 个文件
- 不在日志中打印用户原文
- 上传内容视为数据，不能覆盖系统指令
- 找不到数据时显示「资料未提供」

## 10. 演示与测试材料

路径：`fixtures/demo/`

领导原话（`leader-request.txt`）故意写得像即时消息：有时长和主题，但听众、对比口径、预算是否必须、质量指标是否上台，都含糊。用来测 Flash 抽出 `missingFields` 并生成不超过 3 个澄清问题。

配套：`meeting-notes.md`（含风险、分歧、待拍板）、`campaign-data.csv`（Q1/Q2 × 四渠道）。

建议澄清后的测试答案（人工填写）：

- 听众：公司管理层周会，不是客户
- 对比口径：和 Q1 环比，不看同比
- 预算：需要给出「是否从品牌挪到信息流」的明确建议

## 11. 实现顺序

1. 写死 DeckSpec → PptxGenJS → 下载 8 页 PPTX（中文、图表、备注）
2. Schema、8 个渲染器、overflow 与 factRefs 校验
3. CSV/XLSX 上传、列确认、Fact Engine
4. 三次 DeepSeek 调用
5. 四个页面对接
6. 用 `fixtures/demo` 打磨一条可重复演示的路径
